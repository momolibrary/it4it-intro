核心 · 先对版本，再记名字

价值流有 4 条，
也有 7 条——先看你读的是哪一版

老版本 IT4IT 2.x（v2.0 2015 / v2.1 2017）讲 4 条价值流： S2P、R2D、R2F、D2C。新版本 IT4IT 3.0（2022）围绕数字产品重组为 7 条： Evaluate、Explore、Integrate、Deploy、Release、Consume、Operate。 这一页以 v3.0 的 7 条为主线，把 4 条作为历史背景和对照，并给出 4 → 7 的对应关系。

先把版本对齐：4 条是 v2.x，7 条是 v3.0

这不是“两种说法都对”，而是两个版本。先记住版本，再记名字，就不会被“IT4IT 到底几条价值流”绕进去。

老版本 · IT4IT 2.x（v2.0 2015 / v2.1 2017）

4 条价值流（历史背景）

这一版把 IT 的价值链切成四段，缩写最好记，也是很多中文资料仍在引用的口径。

  • S2P · Strategy to Portfolio：战略到组合，决定投什么、不投什么。
  • R2D · Requirement to Deploy：需求到部署，把确定要做的东西设计、建造、测试、上线。
  • R2F · Request to Fulfill：请求到履约，把服务发布成商品并完成订阅、交付、计费。
  • D2C · Detect to Correct：发现到纠正，监控、诊断、变更、恢复。
新版本 · IT4IT 3.0（2022）

7 条价值流（主线）

v3.0 围绕“数字产品（Digital Product）”重组，把原来藏在四段里的环节提升为独立价值流。这一页以这 7 条为主线。

  • Evaluate · 评估：组合与投资
  • Explore · 探索：产品方向、设计与路线图
  • Integrate · 集成：构建并集成 Product Release
  • Deploy · 部署：把发布实例化到运行环境
  • Release · 发布：发布 Service Offer
  • Consume · 消费：下单、订阅、履约
  • Operate · 运营：监控、诊断、修复

4 → 7：到底怎么对应？

v3.0 不是把 4 条简单改名，而是围绕数字产品重新切分。下表按“职责”对照，不是官方逐条改名表。

v2.x（4 条）v3.0（7 条）对应关系
S2P · 战略到组合 Evaluate · 评估 组合评估、投资排序、治理留在 Evaluate：回答“投什么、投多少”。
S2P 选型 + R2D 需求/设计 Explore · 探索 把“选型 + 需求 + 设计”合并成产品探索：Scope Agreement、Product Design、Product Backlog、Release Roadmap。
R2D · 开发/集成/测试 Integrate · 集成 构建、配置、集成、测试，产出 Product Release。
R2D · 部署 Deploy · 部署 把 Product Release 部署到目标环境，形成 Actual Product Instance。
R2F · Offer 发布 Release · 发布 发布或更新 Service Offer，定义服务与消费者的生命周期交互。
R2F · Request/Fulfill Consume · 消费 下单、订阅、履约、计费，形成 Service Contract 与 Chargeback Contract。
D2C · 发现到纠正 Operate · 运营 监控、诊断、修复 Actual Product Instance，回到服务合同与 KPI。
✦

新增的是哪些？严格说，没有凭空多出三个业务领域。v3.0 是把 v2.x 里藏在阶段中的 Explore（产品探索）、Release（服务发布）、Consume（消费履约）提升为独立价值流，并把 Integrate（构建）与 Deploy（部署）从 R2D 里拆开。注意 Explore 同时承接 S2P 的选型和 R2D 的需求/设计，所以它不是只从某一条老流里长出来的。

所以 4 和 7 不是“谁对谁错”，而是版本不同；引用时最好带上版本号。

v3.0 的 7 条：主线

先记这 7 个动词。每条都给下一站一个明确交接物，串起来就是数字产品的生命周期。

01 · 评估

Evaluate · 数字产品组合评估

持续评估整个数字产品组合，让投资跟着业务战略走：投什么、投多少、哪些该退场。

接手：战略、需求、技术机会、预算 → 交给：组合投资计划 + Scope Agreement（给 Explore）

02 · 探索

Explore · 数字产品探索

把已接受的投资细化成产品设计、待办和发布路线图，探索新功能与未来方向，让产品设计持续演进。

接手：Scope Agreement、Portfolio Backlog Item → 交给：Product Design + Product Backlog + Release Roadmap（给 Integrate）

03 · 集成

Integrate · 产品发布集成

设计、开发、配置、集成并测试新的产品发布，把 Product Design 变成可部署的 Product Release。

接手：Product Design、Product Backlog Item → 交给：Product Release（给 Deploy / Release）

04 · 部署

Deploy · 产品发布部署

把 Product Release 实例化到目标运行环境，并确保所有变更都能追溯到对应的发布。

接手：Product Release → 交给：Actual Product Instance + Service Contract（给 Operate / Consume）

05 · 发布

Release · 服务 Offer 发布

把新的或修改后的 Service Offer 发布给消费者，定义服务与用户之间的生命周期交互。

接手：Product Release → 交给：Service Offer（给 Consume）

06 · 消费

Consume · 服务 Offer 消费

让消费者下单、订阅、履约，把 Service Offer 变成可用的 Desired Product Instance，并完成计费。

接手：Service Offer → 交给：Subscription + Desired Product Instance + Service Contract + Chargeback Contract

07 · 运营

Operate · 实际产品实例运营

让已部署的 Actual Product Instance 持续可用：监控、诊断、修复，满足服务合同与 KPI。

接手：Actual Product Instance + Service Contract → 交给：运行证据、事件 / 问题 / 变更；问题回流 Evaluate / Explore

依据：The Open Group《IT4IT™ Standard, Version 3.0》（C221，2022-10-17）；价值流名称与顺序对照《IT4IT™ Conformance Requirements (Level 1) v3.0》（X236，2023-03）Unit 5–11 核对。各条的一句话职责按标准中的 Value Stream 目的与主干数据对象整理，中文为意译。

v2.x 四条，一条一条看（历史口径）

下面每条都保留了 v2.x 的阶段名和交接物，方便和上面的 7 条对照。

S2P

Strategy to Portfolio

让 IT 的投资组合，跟着业务战略走 —— 决定“我们该投什么、不投什么”。

这一段最容易被忽略：大家总觉得 IT 的价值是从“写代码”开始的。但方向错了，后面全白干。 S2P 要把业务战略翻译成 IT 的服务组合与投资决策，并且主动砍掉不该继续投的东西。

关键功能组件

企业架构（Enterprise Architecture）、政策管理（Policy）、提案（Proposal）、组合需求（Portfolio Demand）、服务组合（Service Portfolio）

产出 / 交接的数据对象

数字服务（Digital Service）：一个“值得投资”的服务定义，带着概念设计交给 R2D。

一句话场景

业务想上 AI 客服，但队列里还有 30 个项目。S2P 负责回答：为什么是它、预算从哪来、哪个老服务该退场。

R2D

Requirement to Deploy

把“值得做”变成“能部署” —— 交付一个可上线、可回滚的服务版本。

这是大多数人最熟悉的一段：设计、开发、测试、发布。IT4IT 的贡献不是发明新流程，而是明确 这一段结束时必须交出什么——不是“上线了”，而是一个有版本、有配置、可追溯的 服务发布（Service Release）。

关键功能组件

项目（Project）、需求（Requirement）、服务设计（Service Design）、源码控制（Source Control）、构建（Build）、构建包、发布组装（Release Composition）、测试（Test）、缺陷（Defect）

产出 / 交接的数据对象

服务发布（Service Release）与服务系统（Service System）：交给 R2F 变成可订阅的商品，交给 D2C 变成要监控的对象。

一句话场景

“客户自助改地址”这个需求，从设计到灰度上线，最后交付的不是一个 URL，而是一个带版本的发布包。

R2F

Request to Fulfill

把 IT 变成“服务经纪商”：服务像商品一样被订阅、申请、交付、计费。

这一段是 IT4IT 最有“商业感”的部分。它要求 IT 把能提供的东西产品化： 有目录、有价格、有 SLA、有账单。员工不该靠“找熟人开权限”，而该像网购一样自助完成。

关键功能组件

服务目录编排（Catalog Composition）、商品管理（Offer Management）、请求归并（Request Rationalization）、履约执行（Fulfillment Execution）、用量（Usage）、计费（Chargeback/Showback）

产出 / 交接的数据对象

服务合同（Service Contract）：IT 与用户之间“我提供什么、什么标准”的正式约定；还有 Offer、订阅、计费合同。

一句话场景

新员工入职，在门户里勾选“标准笔记本 + 邮箱 + VPN”，三天内全部到位，月底自动分摊到部门成本。

D2C

Detect to Correct

让服务始终维持在承诺的水平 —— 发现偏差、定位根因、受控修复。

注意它的名字不是“运维”，而是“发现到纠正”。差别在于：它假设服务一定会偏离承诺， 所以要有一条从“感知偏差”到“恢复承诺”的闭环。这正是 SRE、可观测性想做的事， IT4IT 只是把它放进了端到端价值链里。

关键功能组件

服务监控（Service Monitoring）、事件（Event）、事件单（Incident）、问题（Problem）、变更控制（Change Control）、配置管理（Configuration Management）、诊断与修复、服务级别（Service Level）

产出 / 交接的数据对象

期望服务（Desired Service） vs 实际服务（Actual Service）：D2C 关心的就是这两者之间的差距。

一句话场景

支付接口 P99 抖动 → 自动告警 → 定位到某个实例 → 回滚变更 → 恢复，全程记录在同一个服务对象上。

v3.0 深挖 · S2P → Evaluate ＋ Explore

同一条 S2P，在 v3.0 里被拆成了两条：Evaluate 与 Explore

v2.x 的 S2P 是「战略 → 组合 → 需求 → 选型」一条龙，最后交出一个 Digital Service；到 v3.0，这段“投资决策 → 产品定义”被拆成两段（按职责对照，Explore 也承接原 R2D 的需求与设计）： Evaluate 管“钱和方向”（组合要不要平衡、钱投给谁），Explore 管“方案和路线”（投了之后做成什么样、先做哪块、什么时候发）。 两段之间接力用的不是文档，而是 v3.0 的核心数据对象——范围协议（Scope Agreement）。

※ 官方名称是 Explore（动词，与 Evaluate / Integrate / Deploy / Release / Consume / Operate 并列），不是 “Explorer”。

EVALUATE

评估 · Evaluate

组合层 · 让投资跟战略对齐

持续评估整个数字产品组合，保持组合与业务战略一致，并识别支撑业务 / 技术目标的新数字产品机会。

触发组合规划周期（周 / 月 / 年） 主责产品组合经理（Product Portfolio Manager）
输入 · Inputs
  • 七条价值流送来的需求、改进想法与消费需求
  • 新技术机会、技术生命周期事件（如 EOL）
  • 政策法规、预算约束（Policy / Budget Item）
  • 战略主题 / 战略目标（Strategic Theme / Strategic Objective）
  • 企业架构：架构蓝图、架构路线图项（Architecture Blueprint / Architecture Roadmap Item）
  • 现有产品组合与数字产品现状、供应商与 MSP 协议
输出 · Outputs
  • 组合投资计划（含资金与资源）——交给 Explore 去探索
  • 排好序的数字产品组合 ＋ 架构路线图
  • 合格的组合待办项（qualified Portfolio Backlog Items）
  • 更新后的 Scope Agreement：范围、预算、成本收益、状态
  • 初始预算（Budget Item）：批准后先拨给 Explore 做可行性

典型场景：考虑一个新数字产品 · 合理化产品组合 · 规划组合投资 · 执行产品治理

EXPLORE

探索 · Explore

产品层 · 把投资变成可开工的方案

在 Evaluate 的 Scope Agreement 上继续：把已接受的组合待办细化、做预算、定来源，探索新功能与未来方向，让产品设计（Product Design）持续演进。

触发Scope Agreement 发生变化 主责产品经理（Product Manager）
输入 · Inputs
  • Evaluate 交来的合格、已计划接受的组合待办项
  • 初步 Scope Agreement（含 mandate、预算与范围）
  • 战略方向、企业架构蓝图与路线图项
  • 政策、现有数字产品与产品组合、概念设计与需求
  • 可行性探索所需的资源与初始预算
输出 · Outputs
  • 详细版 Scope Agreement：带优先级的 Product Backlog Items、范围与时间
  • 产品待办（Product Backlog ＋ Product Backlog Items）
  • 发布路线图（Release Roadmap / Digital Product Roadmap）
  • 产品设计（Product Design，可版本化）与批准的架构路线图
  • → 交给 Integrate：批准的 Scope Agreement ＋ 一组已达成一致的 Product Backlog Items，开始做 Product Release

典型场景：调查新产品点子 · 优化现有产品 · 验证可行性 · 退役产品

实战 playbook · Evaluate / Explore

把这两条流跑起来：收集什么、怎么走、产物长什么样

前面讲的是“它们是什么”，这一节讲“怎么干”。先约好图例： 标准 是标准里写明的阶段、数据对象与字段； 实践 是把标准字段翻译成可执行的清单、判据与可视化，属于落地建议，不是标准原文。

① 先收集什么 实践

对应 Gather Influencers：一个规划周期开始前，把下面四组信息收齐——它们大多会落成标准数据对象。

战略与方向 标准对象

  • Strategic Theme / Strategic Objective：Id、Name、Description
  • 业务目标 / OKR 与年度优先级
  • 市场、竞争、技术趋势（SWOT 环境扫描）

需求与机会 标准对象

  • 七条流回流的想法 / 改进 / 需求（含消费需求）
  • Portfolio Backlog Item：Prioritization、Acceptance Criteria、Related Products、Demand Profile、Cost Estimation
  • Requirement：功能与合规要求

约束与政策 标准对象

  • Policy：Id、Name、Description、Applicable Geography
  • Budget Item 与预算约束（Financial Period、Investment Type）
  • 供应商 / MSP 协议；Architecture Blueprint（目标架构）

现状与资产 标准对象

  • Digital Product：Investment Status、Portfolio、Budget、TCO、P&L、Business Criticality、Security Risk
  • 现有 Scope Agreement 与组合健康度
  • Architecture Roadmap Item：Status、TargetDate、Roadmaps

② 五步跑法 实践

阶段名与产物来自标准；每步的“动作 / 过关判据”是落地整理。

01
Gather Influencers汇集影响因子
动作四类输入收齐并去重归并；更新战略路线图（Strategic intent → Architecture Roadmap → Product Roadmap → Release Roadmap）；和业务确认价值与政策要求。
产物Strategic Theme / Strategic Objective（新建或更新）。
过关每条输入都能挂到某个主题 / 目标，或明确标注“本期不做”并留下原因。
02
Identify Gaps识别差距
动作目标 vs 现状：找能力缺口、投资缺口、重复建设、该退役的产品；每个缺口配证据（数据、架构差异、成本）。
产物缺口清单（挂到 Strategic Objective）。
过关缺口有证据、有影响的产品 / 业务范围、有优先级。
03
Propose Investments提出投资
动作给机会 + Scope Agreement 打分：业务价值 / 风险 / 成本 / 时间 / 资源；先判断能否复用组合内现有方案；再和 Portfolio Backlog 统一排位。
产物更新后的 Scope Agreement（含优先级、范围、预算初稿）。
过关每个提案有评分与复用结论，能在 Portfolio Backlog 里找到位置。
04
Define Backlog Mandates定义待办指令
动作把法规 / 指令 / MSP 约束变成 Portfolio Backlog Item 与 Scope Agreement 的强制项；做组合合理化（合并 / 下架）；批准后把初期资金拨给 Explore 做可行性。
产物细化 Scope Agreement、Architecture Roadmap Item、Budget Item（Financial Period、Investment Type、Approved Budget）。
过关每条 mandate 有 owner、有对应 backlog 项；每个批准项有预算与资金来源。
05
Ensure Governance治理把关
动作组合平衡 / 合规 / 风险评审；做 go / hold / kill；把理由写进对象，而不是只写进会议纪要。
产物决策记录（Scope Agreement.Status = approved / rejected / deferred；Digital Product.Investment Status）。
过关每个决策有时间、签字、理由；组合不是“只增不减”。

③ 做到什么程度算合格 实践

必备（没有就不算完成）

  • 能拿出一份组合投资计划：资金 + 资源 + 时间，能回答“这笔钱为什么给 A 不给 B”。
  • 每个 Scope Agreement 核心字段齐全：Id、Description、Business Entity、Proposed / Approved Budget（build / run 拆分）、Status、Context（portfolio / product）。
  • 每个 Portfolio Backlog Item 有 Prioritization、Acceptance Criteria、Related Products、Demand Profile、Cost Estimation，并挂到 Strategic Objective 与 Architecture Roadmap Item。
  • 每个批准项有 Budget Item（Financial Period、Investment Type、Approved Budget、Spend、Forecast）。
  • Digital Product.Investment Status 有明确结论（invest / divest / sustain / retired）。
  • 治理决策留痕：谁、何时、为什么。

加分（做得好会明显不一样）

  • 组合矩阵 / 热力图，一眼看出“该砍谁”。
  • 月度或季度 cadence，而不是一年一次大评审。
  • 有组合合理化记录（合并 / 退役），并回写到 Digital Product。
  • 与架构路线图联动：Architecture Roadmap Item 有 TargetDate。
△

不合格信号：Scope Agreement 没预算、没状态，只在邮件里；Portfolio Backlog Item 没有 Acceptance Criteria 和 Demand Profile；Propose Investments 跳过了复用检查（先看组合里有没有现成方案），导致重复建设；投资追溯不到 Strategic Objective；组合只增不减；决策只存在会议纪要里。

标准自己就点名了这些病：数据质量与一致性差、没有全局组合视图、组合 / 服务 / 产品管理不一致、产品生命周期追踪不起来。

放行闸门 · 机器可判定 标准字段

  • Scope Agreement.Status = approved
  • Approved Budget 已填，且拆成 build / run
  • Context = portfolio 或 product
  • 已关联 ≥1 个 Portfolio Backlog Item（n:m）与 Budget Item（n:1）
  • 下游 Product Backlog Item 已能回挂（1:n）

这些检查不需要“感觉”，全是数据对象的字段——ready 是一个状态，不是一次签字仪式。

④ 优雅的可视化 实践

战略追溯链 · 一笔钱为什么花

Strategic Theme→ Strategic Objective→ Portfolio Backlog Item→ Scope Agreement→ Budget Item

任何一笔预算都能沿链回溯到战略目标；断链就是治理信号，比看一百页 PPT 快。

投资组合矩阵 · 价值 × 风险

业务价值高 ↑
小步试点高价值 · 高不确定AI 客服
重仓高价值 · 低风险ERP 升级
先观察低价值 · 高不确定元宇宙展厅
维持 / 自动化低价值 · 低风险旧报表
风险 / 成本 →

气泡大小 = 预算；颜色区分 GtB（增长）与 RtB（维持）。标准里本来就把资金分成这两类。

资金流 · 从预算到每一行待办

Budget Item（run / dev / overhead）→ Scope Agreement（build / run 拆分）→ Product Backlog Item（budget / actual spend）

同一笔钱在三个对象里各有一段账：组合层看 Budget Item，协议层看 Scope Agreement，执行层看 PBI 的预算与实花。

① 先收集什么 实践

Explore 的触发是 Scope Agreement 发生变化——所以它的输入几乎都围绕这张已谈好的协议。

来自 Evaluate 标准对象

  • qualified Portfolio Backlog Item（已接受、已计划）
  • 初步 Scope Agreement（关联 Portfolio Backlog Item / Budget Item）
  • Budget Item：初期资金与资源
  • Strategic Objective / Theme、Architecture Blueprint / Roadmap Item

其他输入 标准对象

  • Policy（合规 / 安全约束）
  • Digital Product 与 Product Portfolio 现状
  • Requirement 与概念 Product Design
  • 来自 Integrate 的进度反馈（Scope Agreement 变更的触发器）

② 四步跑法 实践

Explore 的节奏是“快循环”：MVP / PoC / 概念服务，快速验证后再定版。

01
Prioritize Backlog Items给待办排序
动作把 qualified Portfolio Backlog Item 和 mandate 细化成 Product Backlog Item（epic / feature / story）；用 Evaluate 拨的预算做可行性；检查价值、风险与治理（技术、安全、可靠性、可支持性）。
产物带优先级的 Product Backlog Items + Scope Agreement（scope / timing 细化）。
过关每个 PBI 有 Acceptance Criteria、估算、依赖，并能追到 Portfolio Backlog Item。
02
Define Digital Product Architecture定义产品架构
动作定义 Product Design：逻辑组件、接口、非功能要求（安全 / 隐私 / 可用性 / 性能）；原型、UX、数据模型都要版本化。
产物Product Design（Version + Artifacts）。
过关设计有版本、有 artifacts 清单、NFR 可测；关键评审通过。
03
Refine Product Backlog细化产品待办
动作拆工作包（epic → feature → story）；按需调整 scope、business case、budget；把 PBI 挂到 Product Release。
产物字段齐全的 Product Backlog Item：Type、Parent Id、Priority、Value、Size、Definition of Done、Budget / Actual Spend、Start / End。
过关每个 PBI 能放进一个迭代，有 DoD 与依赖关系。
04
Finalize Roadmap & Scope Agreement定版路线图
动作定版 Scope Agreement；排 Release Roadmap（scope / 依赖 / 资源 / 日期）；干系人 buy-in；建立跟踪与变更机制，然后交给 Integrate。
产物approved Scope Agreement + 定版路线图 + 交接包。
过关Status = approved；路线图有日期 / 依赖 / 资源；Integrate 接手时不需要再问“做什么”。

③ 做到什么程度算合格 实践

必备（没有就不算完成）

  • Scope Agreement 从 created / proposed 走到 approved，含 budget（build / run）、scope、timing、context。
  • Product Backlog 至少三层（epic / feature / story），每条有 Type、Priority、Value、Definition of Done、Acceptance Criteria，并关联 Requirement。
  • Product Design 有 Version + Artifacts（UML / 数据模型 / UX / 原型）+ 可测 NFR。
  • Release Roadmap 有里程碑、依赖、资源；每个 PBI 关联到唯一 Product Release。
  • 与 Evaluate 的 Portfolio Backlog Item、Strategic Objective 双向可追溯。
  • 交接三件套：approved Scope Agreement + agreed Product Backlog Items + Product Design 版本。

加分（做得好会明显不一样）

  • PoC / MVP 的验证记录（快循环的证据）。
  • 假设 / 风险清单，以及验证 / 证伪的结论。
  • Architecture Blueprint 随探索更新。
  • 干系人提前 buy-in（评审记录、签字）。
△

不合格信号：Scope Agreement 还是 created / proposed 就开工；PBI 没有 Acceptance Criteria / DoD / 估算；Product Design 只有一份 PPT、没有版本；Release Roadmap 只有日期、没有依赖与资源；Scope 变更没有回写 Scope Agreement；Explore 变成第二个 PMO——强求完整设计才允许开工，而标准要的是快循环 + PoC / MVP。

交接闸门 · Explore → Integrate 标准原文

  • Integrate 收到的是 approved Scope Agreement，不是一个“backlog”
  • 并附 agreed set of Product Backlog Items（每条有 Title / Type / Size / Priority / Value / Definition of Done）
  • Product Design 有 Version + Artifacts，PBI 能挂到设计元素
  • Release Roadmap 有资源分配与日期，并已得到干系人认可
  • 若协议无法兑现，变更由 Explore 拥有：改范围 / 时间 / 预算或供方

评审时不用翻 80 页 PPT：从 Vision 到 Roadmap 一条线，任何一格说不清就是探索还没做完。

追溯链 · 从战略目标到 Release

Strategic Objective→ Portfolio Backlog Item→ Scope Agreement→ Product Backlog Item→ Product Release

标准原关系：Portfolio Backlog Item ↔ Strategic Objective / Architecture Roadmap Item；Scope Agreement ↔ Portfolio Backlog Item / Budget Item / Product Backlog Item；Product Backlog Item → Product Release。串起来就是一条可审计的链。

为什么 v2.x 这四条能覆盖整个 IT？

这是 v2.x 的回答；v3.0 用 7 条把同样的覆盖范围拆得更细，但“横跨部门、有交接物、可度量”这三条判断没有变。

它们横跨部门，而不是复制部门

开发、运维、服务台、财务、架构团队……在同一条价值流里都只是“某个阶段的参与者”。这样描述出来的 IT 才是一个整体，而不是一张组织架构图。

每一段都有明确的“交接物”

S2P 交 Digital Service，R2D 交 Service Release，R2F 交 Service Contract，D2C 交 Desired/Actual Service 的差距。交接物清晰，才能度量、才能自动化。

可以单独改造，不必推倒重来

你完全可以只优化 R2F（先把服务目录和订阅做起来），其他三条不动。这正是 IT4IT 声称“可落地”的原因。

能算出“价值流”的账

一旦数据按对象串联，就能算出每条流的时间、成本、返工率。这比“按部门分摊预算”有用得多。
