答案 · 第一层

制造业有供应链，
IT 也该有价值链

一家汽车厂不会按“冲压车间、焊接车间、喷漆车间”来回答“我们怎么创造价值”， 它会画一条从原材料到客户的供应链。因为只有端到端的视角，才能看出哪里堵了、哪里浪费。 IT4IT 做的事一模一样：它不按部门给 IT 画组织架构图，而是画一条端到端的价值流。

一张图记住 IT4IT 的三层

点开每一层，看看它各自回答什么问题。

L1

IT 价值链 · IT Value Chain

IT 的价值是怎么产生的：从“决定做什么”到“交付出去”，再到“一直保持好用”。（点击展开）

回答的问题是：价值从哪来、流经哪些环节、最后交付给谁。

IT4IT 把它拆成 4 条端到端的价值流，每一条都能独立回答“从哪里开始、到哪里结束、产出什么”。这 4 条价值流横跨所有部门，所以它能描述整个 IT，而不是某个团队的局部。

  • S2P — 决定“我们该投资什么”
  • R2D — 把决定变成可部署的服务
  • R2F — 把服务变成员工随取随用的东西
  • D2C — 保证已经交付的服务一直可用
L2

功能组件 · Functional Components

支撑每条价值流的“能力模块”，比如“服务组合管理”“需求管理”“服务发布管理”。（点击展开）

回答的问题是：为了把这条价值流跑通，IT 必须具备哪些能力？

注意一个关键区别：功能组件不是工具，也不是产品。组件是一份“能力说明书”，规定这块能力要接收什么、产出什么、和谁交接。具体用哪家厂商的工具来实现，是你的自由。

  • 同一个组件，可以用商业套装、开源工具，甚至一张表格 + 人工流程实现
  • 换工具不等于改架构——只要组件之间的接口约定不变
  • 这才让 IT4IT 能“几十年不过时”：它描述的是稳定的能力，不是会过期的产品
L3

数据模型 · Data Model

组件之间交接的到底是什么：需求、设计、发布、服务合同……以及它们之间的关系。（点击展开）

回答的问题是：能力之间靠什么“传话”，才能不失真？

这是 IT4IT 最容易被低估、也最有价值的一层。它定义了一组数据对象（例如需求、服务设计、服务发布、服务合同），并规定它们怎么流转、怎么被引用。

  • 有了共同的数据对象，“交给下一个团队”才不是交一份 Excel
  • 同一个对象只维护一份，别的系统引用它，而不是复制它
  • 价值流才能被度量：因为每个环节都知道自己处理的是哪个对象

为什么偏偏是四条价值流？

因为 IT 对公司的价值，只可能往四个方向流。你可以用四个动词记住它：

① 决策

该投什么？

从业务战略出发，决定 IT 投资组合。对应 S2P（Strategy to Portfolio，战略到组合）。

② 建造

怎么把它造出来？

从需求到设计、开发、测试、发布。对应 R2D（Requirement to Deploy，需求到部署）。

③ 消费

员工怎么用上它？

订阅、申请、审批、交付、计费。对应 R2F（Request to Fulfill，请求到履约）。

④ 运行

怎么保证它一直好用？

监控、发现、诊断、修复。对应 D2C（Detect to Correct，发现到纠正）。

✦

关键洞察：这四条不是“四个部门的职责”，而是四条价值流。同一个人可能同时出现在多条价值流里；关键是每条流都有明确的起点、终点和产出物，可以被单独度量和优化。

三层是怎么咬合的？

用一个盖房子的比喻，你可以在 10 秒内把它讲给别人听。

图纸

价值流 = 建筑图纸

规定房子从地基到屋顶要经过哪些阶段，每个阶段交付什么。它不关心砖是谁家的。

工种

功能组件 = 工种清单

水电工、木工、泥瓦工。规定每种活儿要干成什么样、和谁交接，但不指定用哪把电钻。

标准

数据模型 = 管线标准

水管口径、电线规格、接口位置。正是这些标准，让不同工种能无缝接上，而不用现场互相迁就。
